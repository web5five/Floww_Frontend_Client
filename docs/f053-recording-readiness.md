## Source-grounded path for a fresh recording

Each of A, B and C needs its own fresh Task. The journey, chat and voice routes preserve the **same Task within that scenario**; an already-decided Task cannot be switched to run a second case. The old hosted A Task `f17fcaba-7e7e-4efe-8ef6-8bd8ba698e37` has expired authority and an unknown allowance attempt, so its local recovery record, account and chain state must not be reset, replayed or extended. The live operator is the controller, not this audit.

| Case | Fresh Task and policy path | Last safe UI state before any purchase authority |
| --- | --- | --- |
| A, permitted | Request the existing Kiln proposal on a fresh 60 fUSDC mandate, then check that the server actually records `ALLOW` for Pharmacy A on the current mandate and quote. The deterministic simulator's A quote is 23.5 fUSDC; a different or uncertain proposal is not an A success. | The same Task reaches `/journey/{taskId}/approval`; `TaskExecution` is shown only for an eligible `ALLOW` attempt. |

| C, recipient condition | Select Pharmacy C's 19 fUSDC quote. Its quoted pay-to differs from the trusted registry recipient, so `TaskPolicy` returns `RECIPIENT_NOT_ALLOWED`. | The result and chat show the denial, with the same no-account/no-signature/no-payment boundary as B. |

For A, `TaskAccountService.prepare` binds the exact owner wallet, current `ALLOW` attempt, quote, token, recipient, amount and review digest. The Client verifies the returned snapshot, then requires separate owner actions to deploy the account, verify the receipt and bind it, review and sign exact EIP-712 terms, and ask the server to register that delegation on Sepolia. The Client next reads authoritative account funding, sends exact token allowance from the owner wallet, verifies its receipt, sends exact funding to the account, verifies that receipt, rereads the account token balance, creates the idempotent order, requests payment, reconciles the payment receipt, and separately requests/verifies simulated pharmacy fulfillment. A transaction hash, account deployment or paid state alone is not `COMPLETED`; the final Task and Account states and verified payment/fulfillment evidence must agree.

The simulator's quote lifetime is **15 minutes**. The account expiry is the earlier of quote and mandate expiry; Server policy checks both again at account approval and payment. A fresh recording therefore needs an owner wallet with at least the selected 23.5 fUSDC, separate Sepolia ETH for the owner deployment/allowance/funding transactions, and funded configured server executor/reporter signers, all confirmed by the deployment owner without publishing balances or credentials. The deployment owner must verify the actual A recipient/token and healthy protected backend, quote availability, runtime RPC and signer state; a source default or a prior Task does not prove current deployment funding. If the fresh quote or mandate expires, do not extend it or reuse an old signature; the controller must start a new authorized Task.

The Client stores a wallet-operation marker **before** each wallet send and a server-unknown marker **before** approval/payment/fulfillment requests. A missing hash, timeout or unchanged read does not prove that nothing was sent. Existing `*_UNKNOWN` recovery is receipt recheck of the same recorded hash, without a new payment. The F051 audit identifies two unresolved boundaries: a committed server operation can be stranded before broadcast, and a definitive pre-forward rejection can leave a Client marker locked. Neither was reproduced in the current fresh run, and no generic unlock or rebroadcast fix was made here. The old A unknown allowance stays protected for separate read-only investigation.

Voice remains a navigation and conversation aid. It requires an explicit on-screen confirmation, a fresh exact owner/Task/status check, then uses the existing Task flow; it cannot sign, approve, fund or pay. The submitted source keeps voice OFF by default; a separate development build may explicitly enable both UI and server gates. No model suggestion changes a mandate or reviewed terms.
